# 异步调度：控制开始执行的时机

把大量请求先创建为 Promise，再交给 Promise.all，并不会限制它们的并发：请求可能早已开始。限制并发需要掌握任务的启动权，因此这里把 mapper 或 task 作为函数传入。

## pLimit：队列保存启动权，计数保存并发额度

`pLimit(concurrency)` 创建一个可复用的限制器。调用返回的 `limit(task, ...args)` 只提交任务，每次提交都得到自己的 Promise。将这些 Promise 交给 `Promise.all` 可以按提交顺序汇总；也可以逐项处理。函数参数保留泛型推断，同步值、Promise 和 thenable 都通过 Promise 解析过程接入。

实现用 FIFO 队列保存尚未启动的闭包。每次提交或运行任务完成后，都检查是否还有空位：有空位就从队首取出一项，先增加活动计数，再调用它的启动入口。任务函数实际在微任务中执行，因此提交返回后立即观察到的 `activeCount` 包括已经分配额度、等待微任务执行的任务；`pendingCount` 只计算尚未分配额度的排队项。

任务成功、同步抛错或异步拒绝，都先释放名额并尝试启动下一项，然后兑现本次提交的结果。某一项失败不会让整个限制器停摆；如果调用者使用 `Promise.all`，汇总结果可能提前拒绝，但队列仍会继续执行。它与本模块 `mapLimit` 的失败后停止领取策略不同。

`clearQueue(reason)` 拒绝当前所有排队项的 Promise，默认原因为 `Error("Queue cleared")`；活动任务继续运行，后续仍可提交。这是本练习明确选择的行为，不承诺与同名 npm 工具的所有接口或清队列行为一致。调用者仍应观察每次提交返回的 Promise，避免忽略清队列或任务失败产生的拒绝。

并发数必须为正整数，运行中不能动态修改。队列为便于学习使用数组，`shift` 会移动后续项；大量任务可以进一步改为带头指针的队列。不要在并发为 1 的任务内部，再等待同一个限制器提交的子任务，否则父任务占住唯一名额，子任务无法启动，形成死锁。

## mapLimit：多个 worker 共享一个领取位置

先把有限 iterable 转成数组，确保能按输入索引保存结果，再建立最多 limit 个 worker。每个 worker 领取 cursor 指向的位置，立即递增 cursor，执行 mapper 并等待结果，完成后才继续领取下一项。

领取位置的同步步骤发生在 await 之前。对于这里单线程 JavaScript 的执行模型，在这些同步步骤之间不会插入另一个 worker 的异步恢复，所以不需要为 cursor 增加互斥锁。这并不意味着任务在多个 CPU 核上并行运行；它控制的是异步任务的重叠数量。

例如有 A、B、C、D 四项且 limit=2，最初只启动 A、B。如果 B 先完成，就可以启动 C，不必等待 A。结果仍写回各自的输入索引，所以完成顺序 B、C、D、A 不会改变最终结果数组的顺序。

## 提前失败和取消正在运行的操作不同

任一 worker 捕获 mapper 的异常或拒绝后，设置 failed 并抛出，整体 Promise 随之拒绝。其他 worker 下次准备领取时看到 failed，就停止领取排队任务。

已经启动的任务不会凭空停止；它们仍可能完成、失败或产生副作用。要支持真正取消，需要任务配合 AbortSignal 等机制，当前接口没有这项能力。所有 worker 已交给 Promise.all 观察，因此其他 worker 后续拒绝也有拒绝处理链承接；整体提前失败并不意味着已启动操作被取消。[Promise.all 规范](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-promise.all)

输入会先被完整消费，因此不用于无限 iterable 或流式任务源。iterator 在消费时抛错会让返回的异步结果拒绝。空输入返回空数组；limit 必须是正整数，即使输入为空也会验证。

空间主要用于输入数组、结果数组和 worker；假设单项附加空间有界，为 O(n+limit)，实际 worker 数不超过输入长度。总耗时受任务时长与完成顺序影响，不能简单把串行耗时除以 limit 作为保证。

## retry：传任务工厂，才能重新尝试

重试每一轮都重新调用 task，而不是对同一个已经失败的 Promise 反复 await。task 收到从 1 开始的 attempt，retries 代表首次执行之外的额外尝试次数。

| 配置           | 最多执行次数 |
| -------------- | ------------ |
| retries=0      | 1 次         |
| retries=2      | 3 次         |
| 默认 retries=3 | 4 次         |

同步抛错与异步拒绝都进入同一个 catch。达到次数上限，或 shouldRetry 返回 false 时，直接抛出本轮错误；否则等待 delay，再开始下一轮。shouldRetry 接收错误和本轮 attempt；到达次数上限时不再调用它。若它自己抛错，该异常会成为整体失败原因。

间隔发生在前一轮已经失败之后，不是从第一次启动时计算固定节拍。成功则立即返回，不再重试。对于修改服务端状态的操作，应先确定重复执行是否允许；单纯“网络报错”不能证明服务端没有完成上一次操作。

当前版本只提供固定间隔，不包含取消、总超时、指数退避或随机抖动。重试也不是并发控制：需要两者时，先明确限额限制的是整项任务还是每一次尝试，再决定组合顺序。

## runSeries：串行的是启动过程

`runSeries(tasks)` 接收任务工厂组成的同步 iterable，每次 `await task()` 完成后才从迭代器领取下一项，因此活动任务最多一项。结果按执行顺序收集，空输入返回空数组；任务同步抛错、异步拒绝或迭代器抛错都让整体拒绝。循环提前退出还会按 `for...of` 语义关闭迭代器。

如果传入的是已经启动的 Promise，就失去了串行启动的能力。这个练习接受函数集合，不实现上一步结果传给下一步的流水线，也不负责撤销之前已经完成的副作用。

## sleep 与 withTimeout：停止等待和停止工作是两件事

`sleep(ms, signal?)` 注册定时器，到期兑现；信号提前取消则拒绝并清理定时器。成功或取消都会移除监听器，避免长寿命信号持续持有闭包。已取消的信号直接用原始 `signal.reason` 拒绝，不注册定时器。即使延时为 0，也会经过定时器调度，不是同步兑现。

`withTimeout(task, ms)` 把任务结果与超时 Promise 竞争。任务先结束时保留原始结果或错误，并清理超时定时器；超时时拒绝为 `TimeoutError`，随后中止传给任务的 `AbortSignal`。任务可以将该信号传给支持取消的 API。它不接收外部信号，外部取消与超时组合可作为后续扩展。

超时 Promise 先拒绝，再发出 abort，因此取消监听器同步引发的任务拒绝不会抢占超时错误。即使任务忽略信号、之后才拒绝，竞争过程也已为该结果安装处理链；但底层操作仍可能继续产生副作用，超时不等于强制终止任务。若任务执行长时间同步计算阻塞事件循环，定时器也无法及时运行。

这里两个接口的毫秒参数都必须是有限非负数，且不超过 2,147,483,647，避免直接运行于 Node.js 时定时器超范围造成意外短延时。延时只是最早可调度时间，不是精确执行时间；`withTimeout` 的 0 毫秒也不会抢在同步值的 Promise 微任务之前。

## poll：结果没就绪时再查询，失败直接传播

`poll(task, isDone, options)` 首次立即调用 task，attempt 从 1 开始。拿到结果后等待 isDone 判断，满足条件便返回该结果，否则等 interval 再启动下一轮。任务与判断函数都可以异步；只有本轮查询及判断结束才开始间隔，因此不会像盲目使用 `setInterval` 那样叠加未完成的请求。

默认 interval 为 1000 毫秒，maxAttempts 为 10 次总查询次数。maxAttempts 必须为正整数；interval 沿用 sleep 的参数范围。到达上限后拒绝，不再多等一次间隔。查询错误或判断错误直接向外传播，不自动重试。retry 针对失败，poll 针对有效结果尚未满足业务条件；两者不应混淆。

signal 可在开始、查询完成、判断完成和等待间隔时阻止后续轮次。等待间隔中的取消会立即拒绝并清理定时器；查询或判断正在运行时，不会强行打断它们，要等其结束后检查取消。需要取消底层请求时，task 可以通过闭包把同一个信号传给请求 API。若正在运行的操作永不结束，取消信号本身也不能让本实现的返回 Promise 立刻结束。
