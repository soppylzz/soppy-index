# 前端设计模式：识别变化，再选择组织方式

表单提交、消息通知、编辑器撤销、菜单组合都可能出现不断增加的条件分支。设计模式帮助我们明确哪部分变化、谁负责决策，以及不同模块如何协作。它不是要求每个功能都建立一套类层次。

本目录有 13 个独立实现。demo 是可以在 Node 中运行的前端业务机制模型，输出数据与调用顺序，不创建真实 DOM，不发送网络请求，也不提供完整框架。

| 模式 | 前端场景 | 实现 | 主要机制 |
| --- | --- | --- | --- |
| 单例 | 延迟初始化应用内服务 | [singleton.ts](./singleton.ts) | 闭包缓存首次成功创建的实例 |
| 简单工厂 | 根据通知类型建立展示配置 | [factory.ts](./factory.ts) | 集中选择创建规则，返回统一结构 |
| 策略 | 字段切换校验规则 | [strategy.ts](./strategy.ts) | 保持调用方式，替换算法 |
| 观察者 | 状态值变化后通知订阅者 | [observer.ts](./observer.ts) | 被观察对象直接维护订阅关系 |
| 发布订阅 | 业务模块广播保存事件 | [event-emitter.ts](./event-emitter.ts) | 通过事件通道连接发布者和订阅者 |
| 代理 | 拦截表单模型的非法赋值 | [proxy.ts](./proxy.ts) | 在操作到达目标前进行控制 |
| 装饰器 | 给请求函数增加日志 | [decorator.ts](./decorator.ts) | 包装既有行为，保留参数和结果传递 |
| 适配器 | 统一不同版本的接口字段 | [adapter.ts](./adapter.ts) | 将已有接口转换为调用方需要的形状 |
| 命令 | 编辑操作的撤销与重做 | [command.ts](./command.ts) | 将操作封装为可执行、可撤销对象 |
| 状态 | 上传交互的合法状态迁移 | [state.ts](./state.ts) | 当前状态决定允许哪些事件 |
| 责任链 | 认证、日志、处理器逐层执行 | [chain-of-responsibility.ts](./chain-of-responsibility.ts) | 当前环节决定是否向后传递 |
| 外观 | 统一表单校验、提交和忙碌状态 | [facade.ts](./facade.ts) | 向调用方隐藏子流程的协调顺序 |
| 组合 | 多层菜单统一过滤与生成视图数据 | [composite.ts](./composite.ts) | 叶子与容器提供相同操作接口 |

## 单例与工厂：一个控制数量，一个控制创建规则

createSingleton 延迟调用 factory，用 initialized 区分“没有创建”与“创建结果就是 undefined”。第一次成功后，后续参数不再参与创建。同步初始化失败可以重试，初始化过程中递归获取同一个单例会明确抛错。

这里的单例只在一次 createSingleton 调用返回的闭包范围内共享，不等于跨页面、Worker、进程或服务端请求的全局唯一对象。factory 返回 Promise 时缓存的是该 Promise；它日后拒绝并不会自动重新初始化。需要怎样的生命周期，应由业务决定。

createNotification 则每次都返回一个新对象，依据 kind 统一设置 role 和 duration 等配置。这是简单工厂，不是通过继承定义创建步骤的工厂方法，也不是成组创建相关产品的抽象工厂。role 只是交给渲染层的数据，demo 没有验证真实页面的可访问性。

## 策略与状态：为什么都会替换行为，却不是同一个问题

FieldValidator 的调用方始终调用 validate，规则由 setStrategy 替换。required 与 minLength 不需要知道对方的存在。策略适合外部根据需求主动选择算法；如果只有一个稳定规则，直接传函数即可，不必为了模式而增加对象。

UploadController 用状态表实现状态模式的核心思想：允许的事件取决于当前状态。idle 允许 start，uploading 允许 pause、succeed、fail；暂停、成功、失败各有明确的后续路径。不存在的迁移会抛错，并保留原状态。

它没有建立每个状态对应的类，也没有真正上传或暂停网络请求。若未来接入请求，还需要处理取消、过期响应、进度与副作用；不能把修改状态字段当成已经停止了底层操作。

## 观察者与发布订阅：通知关系放在哪里

ObservableValue 自己保存当前值和观察者。set 用 Object.is 抑制相同值的重复通知，回调得到新旧值；subscribe 不会立即补发当前值，需要时通过 get 获取。同一函数重复订阅会由 Set 合并。

通知期间再次 set，会立即更新当前值，但把新一轮通知放进 pending 队列，等当前变化的所有观察者通知完再处理。因此 demo 输出 A:1、B:1、A:2、B:2，而不是让 B 先收到 2 再收到 1。回调参数表示正在通知的变化，get 则可能已经返回后续写入的最新值。

观察者新增与移除遵循快照遍历及执行前检查。观察者同步抛错时，异常向调用者传播，剩余通知被丢弃，已经写入的状态不回滚；finally 恢复通知开关，让后续写入仍能工作。它只观察整个值的替换，不自动跟踪对象内部属性变化，也不等待异步观察者。

EventEmitter 则没有一个被观察的值，发布者通过事件名与参数通知其他模块。每次 on/once 建立独立记录，同一函数重复注册会重复触发；返回的取消函数只移除当前记录，off 会移除该事件下同一函数的全部记录。

once 在执行前移除，避免回调内递归 emit 导致重复调用。emit 先保存订阅快照，新加入者不参与当前轮；尚未执行但已经删除的记录会跳过。监听器同步异常会停止当前轮并向外传播，异步返回值不等待、不收集。emit 的布尔结果表示开始时是否找到订阅集合，不表示任务执行成功。

这两份实现是本目录的教学契约，不是 DOM EventTarget、Node.js EventEmitter 或某个状态库的完整复刻。

## 代理、装饰器、适配器、外观：四种不同的边界

| 模式   | 要解决的问题                       | 本目录的选择                  |
| ------ | ---------------------------------- | ----------------------------- |
| 代理   | 操作能否到达目标，怎样到达？       | 写入前校验字段                |
| 装饰器 | 怎样给现有操作增加附加行为？       | 请求前后记录日志              |
| 适配器 | 已有接口与所需接口如何对接？       | 旧字段与新字段统一为 UserView |
| 外观   | 调用者怎样用简单入口完成多步流程？ | 校验、忙碌控制和提交统一调度  |

createValidatedModel 使用真实 JavaScript Proxy 拦截 set，再用 Reflect.set 保留接收者、访问器和写入失败的语义。未配置的字段直接转发。不要在 set trap 中再向同一个代理赋值，否则可能递归进入自身。[Proxy set 的行为](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Proxy/Proxy/set)

这里是浅层赋值校验：嵌套对象、原对象的直接写入、删除和 Object.defineProperty 都不受同样规则保护。它不提供访问控制或完整响应式系统，输入规则抛出的异常也会直接传播。

withRequestLog 保留 this 与参数，等待结果后记录 success，遇到请求同步异常或异步拒绝则记录 error 并重新抛出。包装器始终返回 Promise，因此会把原本同步的返回形式变成异步。日志回调按同步、正常返回的接口使用；若它自己抛错，异常可能改变请求流程，当前版本没有日志隔离层。这里的装饰器是函数包装，不依赖 TypeScript 装饰器语法。

adapter 中两个转换函数分别理解 LegacyUser 和 ModernUser，输出相同的 id、name、disabled。视图层因而只依赖 UserView。类型声明不验证外部 JSON，demo 没有网络传输或运行时 schema 校验。

createFormFacade 接收校验与提交服务：不合法时返回错误，合法时设置 busy 并提交，最后无论成功失败都释放 busy。忙碌期间的新提交会拒绝，不会被合并或静默丢弃。该约束只在当前 facade 实例内生效，既不取消请求，也不替代服务端幂等规则。

## 命令：撤销的依据必须由操作保存

createReplaceTextCommand 保存替换前的文本，execute 写入新文本，undo 恢复旧文本。CommandHistory 保存已执行栈和已撤销栈；undo 与 redo 在操作正常返回后才移动记录。撤销后执行新命令，会清空重做分支。

操作抛错时历史记录保留，但管理器不能自动回滚操作已经造成的部分修改。这里要求同步命令、每次编辑创建新命令，并通过同一历史管理目标；外部直接修改文本或跨历史复用有状态命令，会破坏撤销的前提。demo 的 AB、A、AB 分别对应执行、撤销和重做。

## 责任链：next 是一次明确的委托

composeMiddleware 让每层决定是否调用 next。不调用就停止向后传递，适合认证失败或已完成处理的短路场景。await next 使下游先完成，再执行本层后半段，因此顺序是 A before、B before、handler、B after、A after。

这是支持回程执行的中间件链，不等于所有责任链都必须有洋葱结构。lastIndex 防止重复委托，下游错误可以由上游包住 await next 的 try/catch 处理。每次运行拥有自己的索引，多个上下文不会共享执行进度。

中间件必须等待或返回 next 的 Promise；脱离链的异步任务不在完成与错误传播约定内。该实现没有 HTTP 服务、路由匹配或请求上下文库。

## 组合：叶子与容器都能生成视图数据

MenuItem 和 MenuGroup 都实现 toView。叶子根据权限决定输出项目还是 null，分组递归处理孩子并去掉空组。上层不需要先判断当前节点是不是分组，再选择另一套调用接口。

菜单输出是普通数据，不是 HTML 或 DOM。过滤菜单只能控制展示，不能代替后端授权。组在构造时复制孩子列表，避免外部数组之后变化影响成员关系；它没有做节点深拷贝，也没有实现环检测，因此要求有限、无环的菜单树。

## 运行与验证

在 `coding/design-pattern/` 中使用以下命令：

```sh
pnpm demo
pnpm demo observer
pnpm demo chain-of-responsibility
pnpm test
pnpm test __test__/command.test.ts
pnpm test:watch
```

[demo.ts](./demo.ts) 输出每个模型的结果和关键顺序，未知名称会失败并列出可用项。[测试目录](./__test__/) 按模式分文件，检查正常流程以及初始化失败、通知重入、非法状态、重复 next、失败撤销与重复提交等边界。类型检查统一在根目录运行 `pnpm typecheck`，不为本子包新增 tsconfig。
