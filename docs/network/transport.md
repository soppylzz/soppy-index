# TCP 与 UDP：可靠字节流和报文

## 1. 两种服务

TCP 向应用提供有序、可靠的双向字节流；没有“一个 `write` 对应一个 `read`”的消息边界。UDP 保留数据报边界，但不承诺到达、顺序或不重复。UDP 头包含源端口、目标端口、长度和校验和；TCP 头还有序号、确认号、窗口、标志位及选项。UDP 上也能由上层实现可靠性，QUIC 就是例子。

选型看需求：文件与普通 HTTP 需要可靠字节流；实时媒体更看重延迟，丢失的旧帧可能没有重传价值，但信令或关键帧仍可能需要可靠交付。不能简单说“UDP 一定更快”；拥塞控制、安全和环境限制仍需处理。

## 2. TCP 如何建立连接

```text
客户端                         服务端
SYN, seq=x                 →
                           ← SYN+ACK, seq=y, ack=x+1
ACK, ack=y+1               →
```

三次握手使双方确认彼此的发送与接收能力并同步初始序号；服务端处理 SYN 后可有半开状态，握手完成后才是已建立连接。SYN 会消耗一个序号。实际包可能带 MSS、窗口扩大、SACK、时间戳等选项。TLS 握手是随后（或 QUIC 中集成）的另一件事。

## 3. 可靠性、窗口与速度

序号标记字节位置；ACK 表示下一期望字节。发送方保存未确认数据，按超时或快速重传等机制补发。接收方可以延迟确认、乱序缓存；SACK 能指出已收到的非连续块。因为 TCP 是字节流，应用必须自己用长度、分隔符或协议帧切消息。

- **流量控制**保护接收方：接收窗口 `rwnd` 表示它还能接收多少。
- **拥塞控制**保护网络路径：拥塞窗口 `cwnd` 限制发送方未确认数据量，算法根据反馈调整。
- 实际在途数据量受两者共同限制，近似不超过 `min(rwnd, cwnd)`。RTT、丢包、带宽和应用写入节奏共同影响吞吐。带宽时延积描述充分利用链路所需的在途数据量。

面试常问“为什么有了流量控制还要拥塞控制”：接收者有空不代表中间链路不拥堵。也不要把某个拥塞算法（如 CUBIC）说成 TCP 协议唯一规定的算法。

## 4. 关闭、半关闭与 TIME_WAIT

一端发送 FIN 表示自己不再发送，但仍可接收；另一端先 ACK，待其也发送 FIN 后再由对端 ACK。所以常见图是四个报文，但 FIN 与 ACK 可合并。`close()`、进程退出和异常 RST 的语义不同。主动关闭方通常进入 TIME_WAIT，以处理迟到报文和可能丢失的最终 ACK；持续时间与实现相关，不要死记固定秒数。大量 TIME_WAIT 不自动等于故障。

## 5. UDP 的细节

一个 `sendto` 对应一个 UDP 数据报；超过路径 MTU 的大数据报更容易遇到分片和丢失。UDP 校验和检测传输错误，并不提供加密或身份验证。DNS、QUIC、WebRTC 常用 UDP，但它们对重传、排序、加密、拥塞的选择各不相同。网络可能限制 UDP，应用应准备降级或中继路径。

## 报文练习

用 Wireshark 的 `tcp.stream eq N` 观察 SYN/SYN-ACK/ACK、序号和重传。抓包位置会影响结果：本机网卡卸载可能让你看到合并/分段前的“超大包”；不能仅凭一个截屏断言线上真实帧尺寸。[抓包指南](diagnostics.md)给出完整步骤。
