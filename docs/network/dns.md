# DNS：从名字到服务入口

## 1. 一次解析经过谁

浏览器/系统先查本地缓存；若没有可用结果，向配置的递归解析器查询。递归解析器可从根、顶级域、权威服务器逐步获得委派和最终记录，并缓存结果。客户端通常不亲自逐级问根服务器。“递归”描述解析器对客户端承担最终答复责任，“迭代”描述它向其他服务器逐步查询的方式。

```text
应用 → 系统 stub resolver → 递归解析器
                           ↘ 根 → TLD → 权威 DNS
```

DNS 记录有 TTL，缓存可存在于浏览器、操作系统、递归解析器等不同位置；记录变更后各处不同时过期。负面应答也可缓存。因此“我改了 DNS，为什么还没生效”先查实际问到哪台解析器、答案 TTL 和权威结果。

## 2. 面试常用记录

| 记录         | 用途               | 易错点                                                |
| ------------ | ------------------ | ----------------------------------------------------- |
| A / AAAA     | IPv4 / IPv6 地址   | 同名可返回多个地址；不保证客户端选第一条              |
| CNAME        | 名称别名           | 不能把它直接当作 IP 地址；有使用限制                  |
| MX           | 邮件服务器         | 与网页访问无关                                        |
| NS           | 指定权威服务器     | 委派与缓存会影响更新路径                              |
| TXT          | 文本策略/验证      | SPF、域名验证等常借用它                               |
| HTTPS / SVCB | 服务端点与连接参数 | 可提示 ALPN、替代端点等；客户端支持与部署决定是否采用 |

DNS 回答“去哪里”，HTTP `Host`/`:authority` 回答“要哪个站点”。DNS 记录不能指定 URL 路径重定向；301/302 才是 HTTP 层的跳转。

## 3. 传输和安全

传统 DNS 常用 UDP/53，但大响应、截断后可走 TCP；DNS over TLS、DNS over HTTPS 把到解析器的查询放进加密通道。加密 DNS 保护的是客户端到解析器的链路，不自动保证解析器可信，也不等于 DNSSEC。DNSSEC 用签名验证 DNS 数据来源与完整性，不能隐藏域名或代替 HTTPS 证书验证。

## 4. 一个排障顺序

```bash
dig example.com A
dig example.com AAAA
dig +trace example.com
curl -v --resolve example.com:443:203.0.113.10 https://example.com/
```

最后一条仅在你确知目标 IP 时使用：它绕过本次 DNS 选择，但仍按域名发送 SNI 和 HTTP host，用来区分“解析结果错误”与“服务器/TLS/HTTP 错误”。示例地址是文档保留地址，不能直接用于真实站点。`dig +trace` 的可用性会受本机网络策略影响。

资料：[RFC 1034](https://www.rfc-editor.org/rfc/rfc1034)、[RFC 1035](https://www.rfc-editor.org/rfc/rfc1035)、[RFC 9460（SVCB/HTTPS）](https://www.rfc-editor.org/rfc/rfc9460)。
