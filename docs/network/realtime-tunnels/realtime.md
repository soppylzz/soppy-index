# 实时通信：先确定数据向哪边流

订单状态每分钟更新一次，和协作编辑每秒传多条操作，不需要相同方案。“实时”描述业务对延迟的期待，不是某个协议提供的硬时限。先问谁主动产生消息、双方是否都需要持续发送、能否接受代理中继。

## 从轮询开始理解持续推送

短轮询周期性发送 HTTP 请求，服务端立即返回当前状态。实现简单，但更新时间受周期限制，没有变化时仍消耗请求。长轮询让服务器等到事件或超时才返回，客户端收到后重新请求；它减少空查询，却仍要处理重发与空窗。

如果事件主要由服务端产生，可以让一个 HTTP 响应持续输出，这就是 [SSE](sse.md) 的方向。如果客户端也要频繁发送独立消息，[WebSocket](websocket.md) 提供双向消息通道。若目标是浏览器之间传媒体或 P2P 数据，[WebRTC](webrtc.md) 还要处理候选地址、NAT 穿透和媒体传输。

| 方式          | 数据方向               | 常见用途             |
| ------------- | ---------------------- | -------------------- |
| 轮询 / 长轮询 | 客户端查询，服务端响应 | 低频状态             |
| SSE           | 服务端持续推送         | 通知、进度、生成文本 |
| WebSocket     | 双向消息               | 聊天、协作           |
| WebRTC        | 对等媒体 / 数据        | 通话、P2P            |

SSE 的单向只描述事件流，页面仍可通过另一个 fetch 提交操作。WebRTC 也可能经 TURN 或媒体服务器转发，不能看到 API 名称就断言端到端直连。

## 长连接把哪些问题交给应用

连接保持得更久，代理空闲超时、网络切换、登录失效、慢消费者都更容易出现。需要明确消息 ID、重连、去重和恢复方式，而不只是加一个重连定时器。

例如聊天消息在服务端保存成功后连接中断，客户端未收到确认。重连后重发可能产生重复；TCP 的可靠传输不能保证业务“恰好一次”。可以使用业务消息 ID，由服务端保存幂等结果，并提供按游标补历史的接口。SSE 的事件 ID 和 WebSocket 的消息序号只是恢复的基础，仍需服务端数据支持。

WebTransport 提供基于 HTTP/3 的流与数据报能力，但它面向客户端与服务器，不能直接代替 WebRTC 的 ICE/P2P 建链。具体可用性需要核对目标平台；本章主线先掌握 SSE、WebSocket 与 WebRTC。
