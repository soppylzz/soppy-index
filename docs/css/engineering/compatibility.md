# 兼容与渐进增强：先有可用结果，再增加能力

不支持某条 CSS 时，浏览器通常忽略相应无效内容，而不是让整份样式都停止。回退设计要利用具体解析规则，并清楚它们的边界。

## 声明回退与运行时无效不是一回事

```css
.panel {
  display: block;
  display: grid;
}
```

不识别 grid 值的浏览器忽略后一条，保留 block；支持时后一条参与层叠。普通未知声明通常局部被忽略，但选择器列表、未知 at-rule 等有各自规则，不能泛化成“任何错误只影响一个单词”。

如果后一条通过 var() 替换后才在计算值阶段无效，浏览器不会重新回到前一条声明。这一类问题见[值处理流程](../properties/processing.md)。

## 用 @supports 保护增强分支

```css
.layout {
  display: block;
}
@supports (display: grid) {
  .layout {
    display: grid;
    grid-template-columns: repeat(2, minmax(0, 1fr));
  }
}
```

基础内容已经可读，条件成立才增强。`supports` 可以组合 and/or/not，也可检测 selector(...) 等具体能力；`CSS.supports()` 在脚本中提供相关检测。

检测接受语法不等于证明所有场景没有实现缺陷，也不说明设备性能足够。检测 Grid 本身更不能证明 subgrid、某种容器查询或新动画语法全部可用。

## 工具处理到哪一层

| 工具或机制   | 能做什么                 | 边界                           |
| ------------ | ------------------------ | ------------------------------ |
| Browserslist | 定义目标环境集合         | 不直接转换代码                 |
| Autoprefixer | 按目标和数据补适用前缀   | 不实现全部缺失布局能力         |
| PostCSS 插件 | 转换具体语法或规则       | 依赖插件，转换可能有语义限制   |
| 脚本补丁     | 在特定结构中模拟部分行为 | 成本、时序和表现可能不同于原生 |

不建议手工给所有属性列一排历史前缀；也不能把容器查询等复杂机制视作添加一个前缀即可补齐。

## 兼容目标要落到关键行为

先确定实际浏览器与设备范围，再查具体语法，最后用最小用例验证关键布局、焦点、缩放和滚动。UA 判断只适合有证据的缺陷规避，不适合普遍推断能力。

渐进增强允许基础体验较简单，但文字、按钮和主要操作应该可用。条件规则见 [CSS Conditional Rules 3](https://www.w3.org/TR/css-conditional-3/)。
