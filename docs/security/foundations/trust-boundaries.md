# 威胁模型：先说明攻击者能控制什么

一个“修改收货地址”的接口用了 HTTPS，也要求登录，但攻击者仍可能改掉别人的地址。TLS 只保护传输链路，不能判断请求中的订单 ID 属于谁。分析安全问题时，应先说明资产和攻击能力，再选择防线。

## 沿一条输入找出信任变化

假设地址修改请求从浏览器经过 CDN、反向代理、应用服务，最后更新数据库。用户能改请求体，也能直接调用 API；攻击者还可能控制另一个站点，引导用户的浏览器发请求。应用不能把“来自页面的字段”当成“已经验证的字段”。

| 位置 | 已有证据 | 仍需判断 |
| --- | --- | --- |
| HTTPS 连接 | 到 TLS 终止方的传输获得机密性与完整性保护 | 终止方之后的连接是否安全，应用逻辑是否正确 |
| 有效会话 | 请求携带可接受的身份凭据 | 是否由用户预期流程发起，主体能操作哪个对象 |
| 通过输入 schema | 字段形状满足约束 | 业务状态是否合法，输出时是否进入危险解释环境 |

若 CDN 终止 TLS，它到源站是另一段连接。若反向代理附加用户身份头，源站还要确保请求只能来自可信代理，不能同时允许外部请求伪造同名头。信任必须由部署和验证支撑，不能由字段名表达。

## 相似结果可能来自不同攻击链

攻击者把自己的请求体订单 ID 换成别人的，是资源授权缺失；诱导已登录浏览器提交地址变更，可能是 CSRF；在评论里注入代码后修改地址，则是 XSS。三者都可能导致数据被改，但入口、能力与主防线不同。

因此不要只说“攻击者控制输入”。要进一步说是控制普通文本、HTML、同站子域，还是已经能执行同源 JavaScript。XSS 场景中的攻击者能读取许多页面数据；只有跨站页面控制权时，通常仍受同源读取限制。提升攻击能力假设后，原本有效的防线也可能不再成立。

## 用因果链组织解释

复盘时沿“可控入口 → 解析或信任规则 → 敏感动作 → 防线”展开。例如：外站表单可发 POST，目标 Cookie 在相应条件下自动附带，服务端只检查 Cookie，于是误把身份有效当成用户有意转账。CSRF token 和来源检查切断的是这一步信任，CORS 的响应读取限制没有解决它。

这种分析也能暴露防护边界：输入校验不能代替输出编码，前端隐藏不能代替服务端授权，HTTPS 不能审查页面中的恶意脚本。

## 把资产、威胁、漏洞和风险分开

文档内容是资产，未经授权读取是威胁，接口缺少所有者校验是漏洞；风险还取决于漏洞被利用的可能性与影响。攻击面是可被接触的入口集合，信任边界是数据或权限假设发生变化的位置，两者也不是同义词。

纵深防御让一层失效后仍有其他约束，例如安全输出配合 CSP；最小权限则缩小失效后果，例如只授予必要 scope、减少第三方脚本及返回字段。安全上下文与 iframe 权限的浏览器基础无需在每个攻击章节重复定义。
