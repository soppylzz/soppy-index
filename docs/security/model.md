# 威胁模型：先找信任边界

## 1. 从谁能控制输入开始

攻击者可以控制 URL 参数、表单、评论、上传文件、跨站页面、某些第三方脚本或受污染的依赖，但通常不能直接读取另一源的浏览器内存。威胁模型要明确资产（账号、令牌、业务数据）、入口、攻击者能力和期望防护。仅列“XSS、CSRF”而不说输入从哪里来，难以设计有效防线。

一个典型请求经过浏览器、DNS/CDN/代理、应用服务、数据库。HTTPS 保护传输链路的一段；若 CDN 终止 TLS，CDN 到源站是另一条连接。应用的认证只回答“你是谁”，授权还要检查“你能操作哪条资源”。隐藏按钮、禁用输入框、前端路由守卫都不是服务端授权。

## 2. 三个常见误解

- **CORS 不是服务器防火墙**。它限制浏览器脚本读取跨源响应，不能阻止 curl 或恶意站点提交所有类型的请求。
- **输入校验不等于输出安全**。同一字符串进入 HTML 文本、URL、JavaScript、CSS 等位置时，解释规则不同；XSS 要按输出上下文防护。
- **加密不等于可信**。TLS 验证连接身份和传输完整性，不审查页面脚本是否恶意、接口是否越权。

## 3. 面试分析模板

先说入口与可控数据，再说浏览器/服务器如何解释它，接着指出被突破的边界，最后说明主防线和纵深防御。例如 CSRF 的核心是浏览器可能自动附加 Cookie，所以服务端要验证请求意图；SameSite、Origin 检查、CSRF token 分别减少不同条件下的风险。详细见 [会话与 CSRF](session-csrf.md)。
