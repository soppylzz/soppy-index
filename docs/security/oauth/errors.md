# OAuth 错误：用户拒绝、交易失效与网络失败怎样区分

用户拒绝授权后，如果应用立刻再次跳到授权页，就会形成难以退出的循环。登录是跨页面事务，需要保留交易状态，并按失败原因决定是否重试。

## 错误来自哪个端点

授权端点在确认回调地址有效后，可以通过回调返回 error 和 state；回调地址不合法时不能继续向它跳转。token 端点则直接返回 HTTP/JSON 错误，不由浏览器跳转传递。

| 错误 | 常见含义 | 合理处理 |
| --- | --- | --- |
| `access_denied` | 用户或服务拒绝授权 | 结束本次流程，允许用户主动重试 |
| `invalid_request` | 参数缺失或格式错误 | 修复请求，不重复相同错误请求 |
| `invalid_grant` | code/refresh token 过期、已用或绑定不匹配 | 检查交易；已失效时重新授权 |
| `invalid_client` | 客户端认证失败 | 检查服务端配置，避免让用户反复登录 |
| `temporarily_unavailable` | 授权服务暂不可用 | 展示可恢复状态，限制重试次数 |

网络超时只说明客户端未得到确定结果，不能证明服务器没消费 code。盲目兑换同一个一次性 code 可能得到 invalid_grant，应通过事务状态避免并发和重复加载，并在结果无法恢复时重新发起交易。

## 用状态表达用户能继续做什么

可以把流程理解为：空闲 → 跳转中 → 校验回调 → 兑换中 → 已认证；失败则进入已拒绝、可重试错误或需重新认证。只有校验 state、预期 issuer 等交易上下文后，才能把错误关联到本次操作；不能信任任意 URL 中的 error 来清除用户状态。

成功后清理回调 URL 的 code/state，消费完成的交易，避免刷新页面再次兑换。并发请求续期应共享一次刷新操作，确定失效后只触发一次状态清理；重放业务请求还要考虑写操作幂等性。

日志记录错误类别、提供方和 trace ID，避免写入 token、code、verifier、Cookie 与完整个人声明。Next.js 等开发服务器可能自动记录回调查询串，生产代理、监控和访问日志也需脱敏；源码没有 console.log 不代表凭据没有进入日志。

本地实验实现部分拒绝与重放处理，没有完整的错误恢复 UI。这些状态用于理解应用应承担的责任，不代表 demo 已覆盖全部分支。

参考：[RFC 6749：授权错误](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2.1)、[token 错误](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2)。
