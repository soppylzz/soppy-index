# WebSocket 安全：握手认证后，为什么每条消息仍要授权

用户连接聊天室时已经登录，随后发送订阅另一个租户房间的消息。如果服务器只在握手时认证，连接就可能成为长期绕过资源检查的通道。

## 握手确定身份，不决定全部消息权限

浏览器 WebSocket 不沿用 fetch 的 CORS 预检与响应读取机制。Cookie 参与握手时，服务端要检查允许的 Origin、有效会话等，防止攻击者页面借用户浏览器建立已认证连接。非浏览器客户端可伪造 Origin，所以来源检查不能替代身份验证。

可使用与会话绑定的短期 ticket，但不要把长期 token 放 URL，以免进入代理和访问日志。使用 wss 保护传输，也不会自动保证订阅权限正确。

## 每条消息仍是外部输入

服务器校验消息 schema、类型和长度，从可信连接状态取得主体，再对 room/document 等资源逐项授权。不能因为客户端发了 userId 或 roomId，就允许以该身份加入房间。

消息大小、发送速率、并发订阅与发送积压都要有界，否则已认证用户也可能耗尽内存或 CPU。错误响应提供可处理的类别，不暴露内部堆栈和敏感内容。

## 长连接还要处理身份变化

token 到期、成员移除或退出后，已有连接不会自动重新握手。系统应明确关闭连接、要求重新认证或刷新订阅权限的时机，不能只让下一条新连接失败。

重连可能重复发送业务动作，ack 只说明约定阶段已确认。对必须避免重复的写入，服务端用幂等键、序号或持久化去重维护契约；不能把 WebSocket 连接成功当作恰好执行一次的保证。本地身份 demo 没有实现实时通信服务。

参考：[OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)、[RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)。
