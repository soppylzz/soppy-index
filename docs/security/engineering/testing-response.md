# 安全测试与事件响应：怎样证明修复有效

接口要求登录，却允许 Alice 读取 Bob 的文档。普通“登录成功”测试不会发现问题，因为漏洞在主体与资源的关系中。安全测试需要主动构造系统本不该接受的操作。

## 从滥用场景选择检查方式

先确定资产、入口与攻击者能力，再写 abuse case，例如替换文档 ID、删除 CSRF token、重复回放授权码。每个案例都应说明被保护的边界与拒绝后的状态，不能只断言返回了某个状态码。

| 方法               | 能提供什么线索                 | 不能单独证明什么         |
| ------------------ | ------------------------------ | ------------------------ |
| SAST，静态代码分析 | 危险 API、可疑数据流与代码模式 | 真实业务权限关系一定正确 |
| DAST，动态应用测试 | 运行时请求、响应与可利用行为   | 未触达路径没有漏洞       |
| SCA，软件成分分析  | 依赖版本、已知漏洞与来源风险   | 锁定依赖一定无恶意逻辑   |

DevTools 适合观察 Cookie、CSP、请求与浏览器阻断，代理或 HTTP 客户端可修改和重放请求。HTTP 客户端不会执行浏览器 SameSite/CORS 规则；自动扫描也难以理解复杂租户、成员关系和流程顺序，因此要结合人工分析与行为回归。

## 修复根因，而非只隐藏现象

越权修复应在服务端增加资源约束，再验证本人成功、他人失败、未登录失败和批量入口。XSS 修复应追踪输入到 sink，不能只过滤一个测试 payload。测试范围与权限应明确，危险用例在隔离数据与环境执行。

## 发生泄漏后，先切断仍在发生的损害

事件处置可包括禁用入口、隔离受影响版本、撤销会话与 token、轮换秘密，并保留脱敏证据。回滚代码不等于收回已泄漏的凭据；删除浏览器 token 也无法处理攻击者持有的副本。

按可利用性、影响和暴露范围确定优先级与通知路径。复盘记录时间线、信任判断如何失效、修复后怎样验证，避免只归因于个人或只增加一条泛泛检查规则。

本地 demo 的测试能证明选定请求路径符合断言，不能代替生产安全审计，也不能把未进行的浏览器走查写成测试通过。
