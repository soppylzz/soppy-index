# 文件上传：图片选择器不是服务端安全校验

用户在浏览器里选择了一张头像，服务端收到的仍是一组不可信字节。扩展名、浏览器的类型提示和用户选择动作都不能证明内容适合在本站提供。

## 上传文件从字节变成同源内容

前端的 `accept`、文件名扩展名和 MIME 提示都可伪造；服务端要限制大小、检测实际内容、生成安全文件名、隔离存储，并按业务决定扫描/转码。直接以内联 HTML/SVG 提供用户上传内容可能执行脚本；下载时设置正确 `Content-Type`、`Content-Disposition` 与 `nosniff`，必要时使用隔离域。对象 URL 用完要 `URL.revokeObjectURL`，这解决资源管理，不等于文件安全。

## 沿一份头像上传串起边界

例如用户上传头像：浏览器 accept 只改善选择体验；服务端验证实际内容和大小；存储时生成安全名称；显示时使用适当类型与隔离来源；替换或删除时检查资源所有权。若后端还支持“从 URL 导入头像”，又多了一次需要防 SSRF 的出站请求。每次转换都要重新说明信任依据，不能指望最初的一次校验覆盖后续所有解释方式。用 DevTools 看最终响应头和 Cookie 属性，再用服务端测试验证越权、CSRF token、上传类型与重定向。浏览器 UI 隐藏和源码审查只能提供线索，不能代替服务端验证。

下载接口还必须按文件归属检查权限，随机文件名只能降低猜测概率，不能替代授权。富文档转换和图片处理本身也会调用解析器，应限制资源消耗与处理权限，避免把恶意文件变成解析服务的输入攻击。

## 文件名与解压结果也属于输入

不要直接把用户文件名拼成服务器路径，否则 ../ 等路径片段可能导致穿越或覆盖。由服务端生成名称和受控路径，限制类型、数量与大小；magic bytes 只是一层信号，也不能单独证明整个文件无害。

压缩包上传很小，解压后却可能耗尽磁盘或 CPU。处理时限制展开总量、层级、耗时与输出路径，在隔离权限下执行。HTML、SVG 或含主动内容的文档需按风险转换、隔离或强制下载，不能认为扩展名为图片就可以同源内联。
