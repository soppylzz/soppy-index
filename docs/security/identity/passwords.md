# 密码验证：服务端怎样接受一次身份声明

登录表单中填入 Alice 的邮箱，只是在声明身份。密码验证则尝试证明请求方掌握与这个身份关联的秘密。客户端表单校验不能完成这项证明，因为请求方可以绕过表单直接调用接口。

## 密码为什么不能直接加密或做一次快哈希

若数据库保存明文密码，泄漏后攻击者可立即尝试登录；若保存可逆密文，密钥泄漏也会恢复密码。密码验证通常不需要恢复原文，而是使用适合密码的慢哈希算法，根据本次输入计算派生值并比较。

随机 salt 让相同密码得到不同结果，阻止预计算表被直接复用；它可以与哈希值一起保存，不是第二份秘密。工作因子增加每次猜测的计算或内存成本，需要根据部署能力评估。单次 SHA-256 太快，即使加 salt，仍便于攻击者离线大量猜测。应使用维护良好的 Argon2id、scrypt 等实现，而不是自行设计组合算法。

实验用 scrypt 验证两个固定账号，保留显式步骤帮助理解；它没有数据库注册、工作因子调优或完整账号管理。密码随机 salt 与随机会话 token 的哈希索引解决不同问题，不能因为后者用了 SHA-256 就认为密码也适合照搬。

## 登录接口如何避免成为猜测工具

在线限速限制攻击者提交次数，慢哈希限制数据库泄漏后的离线猜测，两者作用阶段不同。错误提示不应轻易暴露账号是否存在，响应时间、重置接口和其他入口也可能泄漏同类信号。只统一一条文案不能自动消除所有枚举途径。

登录 CSRF 可能让受害者进入攻击者账号，再把自己的资料写进去。本地登录接口也应验证请求来源或适用的 CSRF 证明，而不是只保护登录后的转账接口。实验登录 POST 要求 Origin 精确等于应用源，验证成功后撤销旧会话并生成新标识。

## 找回密码与二次认证也是身份入口

密码重置凭据应不可预测、短期、单次使用，并防止出现在第三方日志与 Referer 中。是否撤销已有会话要按风险明确规定。修改邮箱、绑定身份提供方等操作通常需要确认当前账号控制权，不能仅凭一份长期未重新确认的会话完成所有高风险动作。

MFA 引入其他验证因素，但并非所有因素都抗钓鱼；一次性验证码仍可能被实时中继。WebAuthn/通行密钥通过与依赖方标识关联的公钥凭据进行认证，私钥不作为共享密码交给服务端。账号恢复仍可能成为较弱入口，所以增加一种登录方式并不自动保证整套账号体系的强度。

面试解释密码安全时，应把数据库泄漏后的离线猜测、在线撞库、账号恢复和会话被盗分开；它们需要不同防线。不能用“HTTPS 已经加密”回答服务端凭据如何存储。
