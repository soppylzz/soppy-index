# JWT：解码成功与验证成功之间差了什么

把 token 粘进解码工具就能看到 `sub` 和 `role`，为什么服务端还要验签？因为编码只解决表示问题，任何人都能自己生成一段带有管理员声明的 JSON；验证才决定这些声明能否被本应用接受。

## 从可读声明到可信发行者

常见签名 JWT 使用 JWS Compact Serialization，由 `header.payload.signature` 三段组成。前两段是 base64url 编码，通常可直接读取；JWT 也可以采用 JWE 加密封装，所以“三段”描述的是常见签名形式，而非所有 JWT。

```json
{
  "iss": "https://id.example",
  "sub": "user-42",
  "aud": "documents-api",
  "exp": 1900000000,
  "iat": 1899996400
}
```

这是声明示意，不能作为可使用的凭据。`iss` 指签发者，`sub` 指主体，`aud` 指接收方，`exp` 和 `iat` 使用秒级 NumericDate。签名将受保护的头和载荷绑定到密钥；只有验证方已经信任签发者及其密钥，这种绑定才有意义。

## 验证是一组相互配合的约束

应用先确定自己接受哪类 token、哪个发行者和哪些算法，再让库验证签名与声明。算法允许列表应由服务端配置，不能让未验证 header 的 `alg` 自行决定安全策略。`kid` 只是从可信密钥集合中选 key 的线索；不能根据任意 `jku` 去下载攻击者的公钥。

随后检查预期 `iss`、`aud`，按 token 类型检查 `exp`、`nbf` 等时间约束，并只允许合理时钟偏差。JWT 基础格式并不强制每个 token 都有全部声明，应用协议必须规定哪些字段必需。OIDC ID token 还需关联 nonce 等上下文；access token 的 scope 与资源权限则由 API 检查。

反例是：服务 A 和服务 B 信任同一签发者，A 只验签，不检查 audience。攻击者拿到签给 B 的有效 token，也可能被 A 接受。签名没被伪造，接收方边界却被突破了。因此“验签通过”不等于“本次操作已授权”。

JWKS 轮换需要兼顾缓存和旧 token 有效期；遇到未知 `kid` 可以受控刷新，但不能每个随机值都无限触发远程请求。密钥获取失败时不能跳过验证。

## 离线验证的收益与撤销代价

签名 token 可以在不查询会话表时验证，这有利于多个资源服务独立处理请求。代价是服务端若只看签名和过期时间，用户退出或被撤权后，旧 token 仍可能有效。短有效期缩小窗口，撤销列表、版本检查或 introspection 提供在线控制，同时增加状态依赖。

签名不保密，也不阻止 bearer token 被复制后重放。敏感信息不应放入可读 payload，token 也不应进入 URL、访问日志或分析上报。JWE 能保护内容机密性，但仍需处理接收方、过期和重放，不能替代这些判断。

## 对称与非对称算法改变了谁能签发

HS256 使用共享密钥做 MAC：能够验证的一方通常也能生成有效 token。RS256、ES256 分别使用 RSA、椭圆曲线私钥签名，验证方只持公钥即可验证，适合不应获得签发能力的多个资源服务。选择依据是信任关系与密钥管理，而非算法名称越长越安全。

JWT 是声明容器，JWS 提供签名或 MAC 保护，JWE 提供加密保护，JWK/JWKS 描述密钥与密钥集合。`jti` 可标识一个 token，但只有服务端维护重放或撤销状态时才产生相应控制，添加唯一 ID 本身不会阻止复制使用。

OIDC ID token 使用 JWT；OAuth access token 可以是不透明值，refresh token 一般应作为不透明凭据使用。客户端不能依赖解析 access token 的内部字段维持协议兼容。

参考：[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)、[RFC 8725](https://www.rfc-editor.org/rfc/rfc8725)。
