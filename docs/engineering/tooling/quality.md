# 质量检查：通过了检查，为什么仍会出错

订单按钮点击后没有提交，可能没有语法错误、类型错误或排版问题。不同检查覆盖不同风险，全部通过也只能说明已检查的范围内没有发现问题。

## 静态检查各有职责

Parser 检查语法，TypeScript 检查静态类型，ESLint 检查代码模式和约束，Prettier 统一排版。Type-aware lint 可以识别一些未等待的 Promise 等问题，但依赖类型分析，成本也更高。

ESLint 的 parser、plugin、rule、config 分别对应解析器、规则提供者、具体检查和启用策略。配置冲突时应看目标文件的最终有效配置，而非只看配置文件里的某一行。

本地 hook 提供快速反馈，CI 负责最终门禁；hook 可以被跳过，不能成为唯一保证。自动修复后也要确认语义，格式工具不会理解业务。

## 用风险选择测试边界

| 测试 | 适合证明什么                 | 容易漏什么             |
| ---- | ---------------------------- | ---------------------- |
| 单元 | 价格计算、状态转移等局部规则 | 接线与真实依赖         |
| 组件 | 用户输入与组件反馈           | 浏览器完整导航和布局   |
| 集成 | 请求、缓存、模块协作         | 生产部署差异           |
| E2E  | 登录、编辑、提交等关键路径   | 大量边界组合与底层细节 |

模拟 DOM 适合快速逻辑验证，不完整实现布局、绘制和导航。焦点、尺寸、拖拽或加载行为需要真实浏览器证据。测试比例取决于风险和维护成本，不必机械追求某个金字塔形状。

## 替身和时间控制的限制

Stub 提供返回值，spy 记录调用，fake 提供简化实现，mock 常包含交互预期。替换过多真实模块，会让测试只证明 mock 配置彼此一致。

Fake timer 控制计时器不等于自动处理所有 Promise 与框架调度。优先等待可观察结果，避免随意 sleep。快照适合稳定可审阅结构，不能代替“提交失败时保留用户输入”这样的行为断言。

覆盖率说明代码被执行过，不说明断言有效。Flaky test 应保留 trace，检查共享状态、未等待异步、时区、网络和选择器；反复重试到成功会掩盖缺陷。

模块替身还受加载时机影响：静态 ESM import 在模块主体前处理，CommonJS 有加载缓存，测试框架又可能转换或提升 mock 声明。已加载模块通常不会因稍后替换依赖而自动重执行，应按框架机制安排替身并清理跨测试状态。

Statement、branch、function、line coverage 分别回答语句、分支、函数和行是否被执行。例如失败分支没有断言，即使覆盖到也无法证明错误提示正确；分支覆盖适合发现遗漏路径，仍不能替代有意义的预期结果。
