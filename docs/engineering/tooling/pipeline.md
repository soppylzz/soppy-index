# 构建链路：源码为什么不能直接上线

订单页面使用 TypeScript、组件语法和 npm 包，浏览器却不认识类型标注，也不会自动去 `node_modules` 查找包。构建工具负责把开发输入变成目标环境能加载的产物。

## 从入口走到文件

```text
entry → resolve/load → parse → transform → link → chunk → optimize → emit
```

先解析依赖指向的文件，再读取、解析源码和转换语法；依赖链接后划分 chunk，最后优化并输出 JS、CSS、图片等 assets。实际工具会交错或合并阶段，这是一条理解职责的主线。

| 名称                  | 主要工作                         | 不自动保证什么         |
| --------------------- | -------------------------------- | ---------------------- |
| Parser                | 将源码解析成 AST                 | 程序业务正确           |
| Compiler / transpiler | 分析、转换并生成代码             | 所有运行时 API 可用    |
| Bundler               | 组织模块图与输出文件             | 产物一定更小           |
| Minifier              | 折叠表达式、移除死代码、缩短名称 | 网络与运行时瓶颈都消失 |
| 类型检查器            | 检查静态类型关系                 | 远端 JSON 一定符合声明 |

Source file 是输入文件；module 是工具识别的模块单元；chunk 是分块单元；bundle 常泛指整个打包结果；asset 还包括非 JS 文件。不要把“打包”理解为只生成一个文件。

## 类型擦除、语法降级和 API 补齐

擦除 `price: number` 后就能生成 JavaScript，但把字符串误传给价格计算仍可能被构建器放行。类型检查应作为独立步骤运行；接口输入还需要运行时校验。

把可选链改写成条件判断是语法转换；让缺少 `Promise` 的环境提供该能力是 polyfill。Browserslist 等目标声明帮助工具选择转换，不能凭空补齐 DOM、权限或所有 Web API。

依赖也属于兼容范围。浏览器在依赖文件上报语法错时，应检查实际入口和目标语法，再决定是否转换该依赖，不必先把整个 `node_modules` 全量编译。

## 兼容目标也包括 CSS 和能力检测

JavaScript 语法、运行时 API、CSS 是三类问题。PostCSS 是转换平台，Autoprefixer 等插件按目标处理支持范围内的 CSS 差异，不能把不支持的布局能力全部变成等价实现。

运行时优先检测需要的能力，再决定启用增强或降级；UA 只提供环境线索，不能证明某 API 存在。为现代与旧环境分别交付产物可减轻现代用户负担，但增加构建、缓存和测试矩阵，只有用户覆盖与收益足够时才值得采用。

## 为什么开发正常仍可能构建失败

开发期优先按需处理和快速反馈，生产期还要做分块、压缩与环境替换。开发时未访问的页面，可能直到生产构建才暴露解析错误；生产分支也可能引用不同依赖。

定位时分别确认输入文件、实际配置、转换结果和最终产物。工具名字只能说明候选能力，完整链路才能解释错误发生在哪一步。
