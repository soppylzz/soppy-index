# CI/CD：怎样让一次发布可追踪、可回退

开发机打包成功之后，仍要确认 CI 能重现同一结果，服务器能完整交付，旧页面能继续使用。

## 先区分三个对象

Artifact 是一次构建的结果，cache 是可丢弃的加速数据，deployment 是把产物放入环境并切换流量。删掉缓存可以重建，丢掉发布产物则可能无法准确回滚。

常见流水线是固定工具版本、冻结锁文件安装、静态检查、测试、构建、部署、关键路径冒烟与线上观察。独立检查可并行，有产物依赖的任务按顺序执行。

Build-time 配置进入产物，改变它需要重建；runtime 配置可让同一产物部署到不同环境，但要校验结构并记录版本。浏览器可见配置不能承载服务端秘密。

## 为什么旧页面会加载不到新 chunk

用户早上打开列表，下午部署后才进入详情。旧 runtime 仍可能引用旧 chunk；如果发布时清空旧资源，这次动态加载就会失败。

因此先上传带 hash 的新资源，再切 HTML，保留仍可能被旧页面引用的资源。HTML 应能及时更新，资源 URL 则尽量不可变。CDN、浏览器与 Service Worker 必须共同考虑，不能只测试全新标签页。参见 [CDN 更新](../../network/delivery-optimization/cdn.md)。

## 灰度与回滚要验证用户路径

滚动发布逐步替换实例，蓝绿通过两套环境切换，金丝雀先验证部分流量。健康检查只证明服务存活，冒烟还应覆盖登录、查询、提交与关键资源加载。

每次发布关联提交、artifact、配置、map 与 release；灰度同时观察错误率、性能和关键业务成功率。回滚要切回匹配的产物与配置，并确认后端接口或数据迁移仍兼容旧前端。

只回滚 HTML 却已经删除旧资源，或者旧前端不能读取新数据，都不算完整回滚方案。故障处理继续读[监控与恢复](../monitoring/operations.md)。
