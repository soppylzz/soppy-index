# 告警与故障响应：把数据变成恢复动作

新版本出现一千条错误，可能来自一个重试循环，也可能影响一千位用户。先看影响与分母，再决定严重程度。

## 聚合与告警口径

Fingerprint 可由错误类型、归一化堆栈与业务位置组合，去掉动态 ID 等噪声；过粗会合并不同故障，过细则制造大量新问题。使用原始位置与映射位置时要保持版本口径一致。

错误率需说明分母是 page view、会话、请求还是业务操作，受影响用户数也要单独看。将新错误、版本回归、持续窗口和最小样本量结合，减少低流量尖峰和告警风暴。

SLI 是测量口径，例如关键提交成功率；SLO 是它的目标；错误预算是目标允许的失败额度。不是所有错误都等价，取消导航或无关图片失败不应自动视为关键流程失败。

静态阈值适合明确的目标，版本对比与周期基线用于识别回归，复杂异常检测仍需可解释与可行动。告警应有 owner、severity、runbook 和升级路径，并用合并、去抖与维护窗口控制噪声；长期无人处理的规则应调整或移除，而非永久静音。

## 先确认 map 与代码属于同一发布

压缩栈还原需要生成文件 URL、行列、release/dist 和对应 map。异步 chunk 也要上传，public path 与资源 hash 应能关联到真实部署产物。

位置明显错误时先核对是否混用了构建结果，而非直接怀疑源码。隐藏 map 注释只能减少发现线索，存储与平台访问仍要控制。这里使用构建时生成并保存的 Source Map，还原位置前先确认它与产物属于同一 release。

## 一次订单保存故障怎样推进

先确认影响的版本、路由、设备与用户比例，判断故障正在扩大还是历史残留。再关联 release diff、堆栈、breadcrumb、请求 ID 与 trace，验证“提交失败”究竟发生在请求前、服务器处理还是响应解析阶段。

缓解可以是关闭高风险 flag、回滚、切备用路径或只读降级。先保护用户数据，再追求根因的完整解释；每次动作之后观察成功率和用户恢复，避免重复提交或刷新造成二次损害。

恢复后验证边缘路径和旧标签页，保留时间线、触发条件、检测缺口与行动项。每条改进有 owner 和期限，runbook 记录症状、仪表盘、缓解与升级路径。

一次可靠的发布还应演练接口超时、CDN 缺失资源和错误配置；只有真正执行过的回退，才能为恢复能力提供证据。这些恢复条件应在 CI/CD 设计和发布演练中提前验证。
