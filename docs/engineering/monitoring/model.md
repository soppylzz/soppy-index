# 监控模型：先问要用数据回答什么

“订单保存失败”可以是一条错误，但只有错误消息，通常不足以解释失败。监控需要把结果、趋势与上下文关联起来。

## 不同信号各有用途

| 信号   | 用途                   | 订单示例               |
| ------ | ---------------------- | ---------------------- |
| Error  | 描述失败及堆栈         | 提交解析异常           |
| Log    | 保存离散事实           | 草稿进入提交状态       |
| Metric | 聚合趋势               | 提交成功率、延迟分位数 |
| Trace  | 关联一段操作的工作单元 | 点击、HTTP、后端处理   |
| Replay | 重建部分操作画面       | 用户在哪个步骤遇到问题 |

业务埋点关注使用行为，可观测性关注系统状态与原因；可以共享受控关联标识，但不必收集同样内容。

事件一般关联时间、release、环境、路由模板、view/session 和必要设备维度。完整路径中的动态订单 ID 不适合直接变成无限增长的聚合维度。

服务端收到事件后，还需校验协议、清洗与去重，再分流到聚合和存储；查询、告警、定位与恢复才形成完整链路。采集量增加不等于可观测性变好，应先确定问题、指标 owner 和行动。

## Breadcrumb 提供异常前摘要

用有界环形缓冲记录近期导航、语义点击、请求和状态变化，异常时附带快照。只记录字段类型或操作发生，不记录输入值、凭据和整份 store。

结构化日志让 message 给人读，稳定字段供机器聚合。限制条数、单条大小和保留期，避免监控反过来耗尽内存。Replay 通常由 DOM 快照和变化重建，不能保证还原跨源 iframe、Canvas 或所有浏览器状态。

日志的 time、level、category、message 和关联 ID 应稳定；debug/info 描述过程，warn 表达风险或降级，error 表达失败，按团队的可行动标准统一使用。Breadcrumb 还要保留时间和小型类别上下文，点击使用语义标识，避免脆弱又冗长的 DOM 路径。

Replay 应作为按需补充：按会话采样、限定时长与字节，评估 DOM 序列化和 mutation 处理的主线程开销；用 session/event ID 与时间关联错误。错误发生后才开启采集无法找回此前画面，若需保留错误前片段，须预先有受限且已脱敏的缓冲。Shadow DOM 等内容能否还原也依实现而异。

## Trace 把前后端接起来

Trace 是一段端到端操作，span 是有起止的工作单元，通过 traceId/spanId 和父关系关联。前端可以在导航或操作时建立 span，将 Trace Context 传给受信后端。

跨源附加 header 可能引起预检，还要限制传播目标。采样策略可能让链路不完整，因此 request ID 仍是实用的定位补充。见 [W3C Trace Context](https://www.w3.org/TR/trace-context/)。

Span 的 status 描述结果，attributes 保存受控维度，events 记录工作单元内的离散事实。头部采样在链路开始时决策，成本低但不知道最终是否出错；尾部采样在收集后选择慢或错误链路，需要后端缓冲和足够完整的 span，不能恢复客户端从未发送的数据。见 [OpenTelemetry 采样](https://opentelemetry.io/docs/concepts/sampling/)。

## SPA 需要自己的 view 口径

URL 改变只是导航开始或过程信号，业务完成还要看关键数据与内容。记录 navigation ID、起点、完成、取消和错误；快速连续导航不能把旧结果计入新页面。

首次硬导航使用 Navigation Timing，软导航要核对浏览器支持或应用定义。页面后台停留、pagehide 与 BFCache 恢复也需统一统计口径，不能把所有停留时间都当作活跃使用。
