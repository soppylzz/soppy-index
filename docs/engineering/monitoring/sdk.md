# 监控 SDK：先保证不会拖垮被监控的页面

上报端点故障时，SDK 如果无限重试和积累事件，会把一次监控故障扩大成业务卡顿。采集、处理和传输都需要上限。

## 一条事件经过哪些阶段

```text
instrumentation → normalize/redact → sample → bounded queue → transport
```

核心管理事件协议与生命周期，插件负责 error、请求和路由等采集。脱敏应在进入持久存储和上报前完成；SDK 的内部失败要隔离，不能修改业务返回值或吞掉业务异常。

包装 fetch、history、console 等原方法时，要保留 this、参数、返回值和原有异常行为，避免重复 patch，并支持卸载。SDK 自身请求应排除采集，防止一次上报又生成下一次上报。

多个 SDK 实例共存时可用共享注册信息协调监听与 patch 所有权，并保留必要的属性描述符。卸载时只撤销自己仍拥有的包装，避免把后安装 SDK 的包装一并覆盖。远程控制采集率要校验来源与配置，失败回到安全默认值，不能接收任意脚本执行。

## 有界队列和受控重试

限制事件数、单条大小、总字节与保留时间，拥塞时优先保留重要错误、丢弃低价值日志。采样要记录策略；只看采样后的条数会误判真实发生率。

运行中可批量发送，失败后只对适合重试的错误退避并加抖动。事件 ID 供服务端去重，重复传输不能重复计数。离线暂存可用 IndexedDB，但还需容量、过期、恢复节流和数据删除策略。

页面隐藏或离开时可尝试 sendBeacon 或 keepalive fetch。Beacon 返回已排队不代表服务端收到，且不能读取响应；keepalive 也有请求大小与生命周期限制。应用被终止时无法承诺最终送达。见 [sendBeacon](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon)。

Transport 使用受控超时与独立失败处理，上报端点异常时限流或暂停；不要借用会触发业务 toast、刷新登录或采集自身错误的拦截器。批处理也需同时按条数、字节和时间触发，避免低流量时事件一直留在队列。

## 数据最小化也降低成本

按字段白名单采集，移除 token、Cookie、输入正文和敏感 URL 参数；Replay 默认遮盖内容，对敏感区域直接阻止采集。脱敏后仍要限制访问、留存和关联能力，匿名或随机 ID 并不自动消除隐私风险。

采集是否需要同意、如何撤回与删除，应由实际数据用途、组织政策与适用要求确认；SDK 提供可停用与清理能力。这里讨论工程设计，不替代具体法律判断。

传输与存储保护、最小访问权限、导出审计和到期删除应贯穿平台；按受控标识执行删除时，也要覆盖索引、离线队列和 Replay 等关联数据。不要为便于检索再扩散完整用户输入。

还要观测 SDK 自身的版本、初始化失败、丢弃量和上报状态，但这些内部指标同样需要限流，避免监控自己的故障形成递归。
