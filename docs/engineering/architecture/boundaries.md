# 架构边界：先问什么会一起变化

订单页面把金额计算、HTTP 调用和弹窗渲染写在一起后，改接口容易影响价格规则，改交互又容易破坏提交。架构的价值是隔离这些变化，并让团队知道规则属于谁。

## 用约束选择结构

先明确业务规模、协作人数、发布频率和生命周期，再比较维护成本、性能、可靠性与安全。两个人维护的短期页面，不必预先建立完整插件平台。

高内聚是一起变化的内容靠近，低耦合是修改一处不必理解全部系统。目录只表达边界，真正边界还要靠公开 API、依赖规则和评审维护。

## 一次提交中的分层

| 职责           | 订单示例                     |
| -------------- | ---------------------------- |
| UI             | 收集输入、呈现进度和错误     |
| Application    | 编排校验、提交和后续刷新     |
| Domain         | 计算可退款金额、判断业务状态 |
| Infrastructure | HTTP、持久化与监控适配       |

并非每个应用都要四套目录。关键是金额规则不直接依赖弹窗和 HTTP 客户端，测试时可以独立验证；应用编排通过明确契约调用基础设施。

依赖反转表示核心描述所需接口，外部实现满足接口。它不要求为每个函数建立抽象类，只有替换、测试或职责隔离确有价值时才引入。

## 按业务组织，再暴露小入口

订单、库存可以各自拥有页面、状态与 API。跨模块只调用公开入口，避免深层 import 私有状态。领域中的同名“用户”也可能分别代表购买者和操作员，应在边界转换模型。

`shared` 适合稳定且无领域归属的基础能力，退款计算仍属于订单。Barrel 导出方便但可能隐藏依赖环和初始化副作用；循环依赖应从职责关系修正，而非只改导入路径。

直接调用适合明确的同步依赖，命令表达执行意图，事件表达已发生事实。全局事件总线减少显式 import，也会隐藏顺序、错误与订阅生命周期；用它之前先确定 owner 和事件契约。

面试描述分层时，沿“点击提交 → 业务规则 → API → 状态更新”解释各层职责，比只画几个文件夹更有说服力。
