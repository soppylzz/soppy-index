# 状态与并发：谁是这份数据的真值来源

订单筛选条件、接口结果和编辑草稿都叫 state，但所有权不同。把它们全部放入全局 store，会让更新、失效和恢复变得模糊。

## 先确定所有权

| 状态       | 合适的位置         | 例子           |
| ---------- | ------------------ | -------------- |
| 局部 UI    | 最近使用它的组件   | 弹窗是否打开   |
| URL        | 路由查询参数       | 搜索词、页码   |
| 服务端数据 | 查询缓存           | 订单列表、详情 |
| 编辑草稿   | 表单或业务模块     | 尚未提交的备注 |
| 持久偏好   | 明确版本的本地存储 | 表格列宽       |

状态放在需要它的最低共同所有者；确有跨模块协调再上移。能从订单项算出的总额不要再保存一份，否则两份数据可能不同步。

实体可按 ID 保存，关系只存 ID，避免列表和详情各维护不同订单对象。Immutable update 只为变化路径创建新身份，方便订阅判断，不等于每次深拷贝全部数据。

## 用状态机排除非法组合

一次提交可约定 idle → submitting → success/error，失败后允许 retry。用一个带状态与对应数据的模型，能避免 `isSubmitting` 与 `isSuccess` 同时为真而没有明确含义；后台刷新与已有数据并存则是另一个维度，不能强行合成单一互斥状态。

订阅也要与使用范围匹配：订单行只选择自己的实体或必要字段，大表单按字段订阅。若每次选择器都创建新的大对象，可能让未变化的消费者也更新；应按状态库的比较规则维护稳定结果，而不是把整个 store 交给全部组件。

## 缓存不是永久正确的数据

查询键要包含所有影响响应的参数，包括租户、筛选和页码等隔离维度。相同键可合并进行中的请求，键不同则不能误合并。

以 TanStack Query 为例，staleTime 决定数据保持新鲜的时长，gcTime 决定非活动缓存保留多久；变 stale 本身不等于立刻发请求，是否重取还取决于挂载、窗口聚焦等触发条件与配置。后台刷新失败时可能仍有旧数据，所以 loading、data、error 并非总是互斥；首次加载状态和刷新状态应分别建模。

写入成功后可精确更新缓存或使相关查询失效。乐观更新适合易预测、可恢复的操作；支付结果不能只凭客户端推测成功。分页缓存要包含页参数，无限列表还要维护 cursor 与顺序。

首次成功但没有结果应显示 empty，已有结果过期则可保留旧值并标识刷新，避免把 stale 当成 error。下一页预取适合高概率导航，应沿用正确查询键与过期策略；提前请求所有可能页面会浪费带宽和服务器资源。

## 搜索 A 为什么覆盖了搜索 AB

```text
request A starts → request AB starts → AB resolves → A resolves
```

A 后返回却属于旧条件。可以取消旧请求，并在提交结果时比较请求序号或查询键；只有仍对应当前意图的结果才写入当前界面。取消能减少浪费，但服务端可能已经执行，不能用 abort 代替业务一致性。

## 乐观更新的回滚也会竞态

用户连续修改两次，第一次失败时直接恢复旧快照，可能连第二次成功结果一起抹掉。可按实体串行写入，或维护操作序列后重新应用未完成操作；不确定时重新拉取并提示冲突。

服务端可用版本号或 ETag/If-Match 拒绝过期写入，前端再提供重新加载、合并或人工确认。重试写操作还需要幂等键，不能只依靠按钮禁用。

跨标签页可通过 BroadcastChannel 或 storage 事件发送版本、失效通知，收到后重新验证，并按操作 ID 去重。消息不提供写入互斥或冲突裁决，不能当作分布式锁；资源版本仍由负责提交的服务端检查。
