# 组件与表单：明确编辑权和公共接口

一个组件同时知道路由、权限、请求、全局状态和弹窗细节，往往很难复用。拆分时先找状态和副作用的所有者，而非机械分成“智能组件”和“展示组件”。

## 受控还是非受控

受控组件由父级保存真值，适合联动和统一提交；非受控组件或 DOM 保存自身状态，适合封装和低频读取。两种方式都可用，但不能没有同步协议地同时维护两份 value。

Props 表达输入，event 表达用户意图，children/slot 表达可组合内容。大量布尔参数可能产生无效组合，适合改成明确 variant 或拆成可组合能力。

Headless 组件负责状态与交互，设计系统组件再加视觉。公共 API 应表达稳定能力，任意访问内部 class 或 store 会让实现细节变成长期契约。

## 表单是一段有生命周期的编辑过程

字段保存 value、touched、error，表单聚合 dirty、submitting，远端选项和提交结果仍归服务端数据层。把服务器订单复制成草稿时，应明确何时初始化、何时重置，后台刷新不能直接覆盖用户正在输入的内容。

同步校验处理格式，跨字段校验表达业务关系，异步校验需防旧响应覆盖新输入。客户端校验提升反馈速度，服务端仍验证全部输入与权限。

动态数组使用稳定 ID；条件字段隐藏时要约定保留值、清空还是不提交。否则用户看不到的旧值仍可能影响结果。

自动保存不仅是 debounce，还涉及版本、失败、重试与冲突。显示“已保存”必须有成功确认；离开提示只在未保存时启用，成功后清理。

Schema 可集中字段和跨字段校验，并为静态类型提供推导来源；类型推导只说明开发期关系，运行时仍需真正解析输入。异步字段校验可 debounce、取消并检查当前值，避免旧“可用”结果覆盖新值；草稿还要明确存储范围、过期和账号隔离。

## 从组件库到设计系统

Design token 表达颜色、间距和字体决策，primitive 提供基础交互，component 组合语义和视觉，pattern 表达重复业务流程。主题使用语义 token，避免业务依赖某个具体色值。

组件默认考虑键盘、焦点、错误提示和 reduced motion；扩展优先组合与明确 variant。升级公共 API 应有版本和迁移说明，视觉回归验证外观，行为与可访问性测试验证能否正确使用。

设计系统还要共享状态矩阵，例如按钮的默认、悬停、焦点、禁用和加载；密度、响应式、国际化与对比度也应纳入组件契约。需要 escape hatch 时限定为 slot、className 或 token 等有边界扩展，避免业务穿透全部内部实现。

破坏性升级结合 SemVer、changeset、迁移说明和必要的 codemod，评估复用率、一致性与交付效率；组件数量多不代表系统成功。
