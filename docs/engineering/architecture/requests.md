# 请求、路由与权限：沿一次导航建立边界

用户打开订单详情，应用需要解析 URL、确认登录、加载数据并显示局部错误。这些步骤相关，却不应全塞进请求拦截器。

## 请求层只统一协议问题

底层 client 处理地址、序列化、响应解析和超时；领域 API 提供 `getOrder(id)` 一类业务调用；页面决定加载与失败如何呈现。

`fetch` 在 HTTP 404/500 时通常仍 resolve，需检查响应状态。错误至少区分取消、网络、HTTP、业务和解析失败，并保留 cause、request ID；不能统一返回空数组，否则“没有订单”和“查询失败”无法区分。

超时应触发取消并释放资源，调用方的 AbortSignal 也要传到底层。重试只针对可恢复且安全的失败，结合退避、抖动和 Retry-After；写操作还要服务端幂等支持。

## Token 过期时不要并发刷新十次

多个请求同时发现凭据失效，可等待同一个刷新 Promise，刷新成功后在受控次数内重放。失败应结束等待并统一进入重新认证状态，不能递归刷新。

重放前确认请求体可重复读取，且写操作不会重复执行。用户登出、切换账号时还要使旧刷新结果失效，避免旧会话重新写回。刷新协议取决于认证方案，不应对所有 401/403 无条件重放。

## 路由承担可分享的页面状态

URL 存筛选、分页与选中实体，短暂 hover 留本地。Route tree 可同时表达布局、加载和错误边界；按路由拆包，避免先加载页面才发现还要串行加载多个必要依赖。

新导航开始时取消旧 loader，并用 navigation ID 限制旧结果提交。首次进入、刷新和深链接都要能加载；history fallback 只处理页面路径，不能把缺失 JS 也回成 HTML。

登录回跳要校验目标来源与路径，局部失败保留布局和可恢复操作。全局错误边界只做最后兜底，不应吞掉所有失败。

Guard 处理导航条件，redirect 规范化或跳转目标，loader 处理数据准备，三者职责不同。403 表达被拒绝，404 表达不存在；是否对无权查看的资源统一返回 404，应按服务端信息泄露策略决定，前端保持一致。

敏感操作可要求近期重新认证，但重新证明身份后仍要检查资源权限；它不能代替授权。

## 权限与功能开关不是同一件事

RBAC 根据角色赋权，ABAC 根据主体、资源、环境属性决策，资源授权还要判断具体订单归属。前端可按能力隐藏或禁用按钮，但每个 API 都必须在服务端检查权限。

Feature flag 控制发布或实验，权限控制谁可访问。新功能对用户开放，不意味着用户可以操作任何订单。权限或账号变化后应清理相关缓存，防止不同身份共用旧数据。
