# 失败、配置与离线：让用户知道当前能做什么

订单列表加载成功，推荐服务失败，不应让整个页面消失。可靠性设计先区分关键路径与可选依赖，再决定如何隔离失败。

## 错误需要恢复语义

输入错误提示用户修改；临时网络故障可受控重试；程序缺陷要上报并提供安全退路。空数据、旧缓存和错误应有不同展示，不能把异常吞成“暂无记录”。

组件或路由边界可隔离局部渲染失败，但框架边界的捕获范围依实现而异，不能假定会捕获所有异步异常。恢复时还要重新确认数据状态，尤其是“提交超时但服务端可能已成功”。

为关键流程设置总等待预算，可选请求独立超时和降级。熔断表示连续失败时暂停请求，bulkhead 表示隔离资源与并发；浏览器端只在确有收益时引入，避免重试放大故障。

## 配置也属于运行输入

明确默认值、环境覆盖和远程配置的优先级，在入口统一解析校验，并记录配置版本。严重错误应阻止错误流程启动，而不是静默采用危险默认值。

多租户和白标将品牌 token、功能能力、接口地址分开。远程 flag 应有 owner、安全默认值与清理期限；配置不可执行任意代码。降级开关自身也要避免依赖已故障的链路。

远程配置还需限制变更权限并校验来源与结构，加载失败时可使用仍适用的最后已知安全版本。配置 schema 升级要有兼容范围；flag 还应记录目标人群与关闭后的业务行为，避免只恢复 UI 却保留后台副作用。

## 离线写入需要完整协议

Online-first 优先服务器；offline-first 保证关键断网流程；local-first 以本地副本支撑即时交互并后台同步。复杂度取决于冲突与同步要求，不由是否用了 IndexedDB 决定。

离线操作写入 outbox，包含操作 ID、基准版本、载荷和状态。恢复后按依赖同步，服务端幂等处理；冲突按业务规则合并或请求人工确认。金额和库存不适合简单按客户端时间最后写入覆盖。

实时消息进入同一查询或实体层，用 revision/cursor 检查重复、乱序和缺口，断线后补增量或重取快照。心跳成功不证明数据已同步，`navigator.onLine` 也不证明接口可达。

冲突策略需要匹配数据：last-write-wins 简单但可能丢修改，字段合并适合互不冲突的字段；CRDT 通过特定数据结构与合并规则支持并发收敛，却不能自动解决库存或支付约束。先确定允许哪些并发操作，再选择同步模型。

实时连接要控制重连退避和心跳；协议如果可能重复交付，客户端仍需幂等处理。关键状态不能只保存在内存连接里，断线后应能通过 cursor 或快照恢复。

界面区分待同步、已确认、失败与冲突。本地 schema、缓存和 outbox 都要考虑迁移；缓存策略继续读 [Service Worker](../../browser/pwa/serviceWorker.md)，链路选择见[实时通信](../../network/realtime-tunnels/realtime.md)。
