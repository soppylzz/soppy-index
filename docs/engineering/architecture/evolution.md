# 架构演进：什么时候值得拆分或重写

代码多并不是微前端的充分理由。先确认独立团队、发布频率和故障隔离需求，再评估物理拆分能否产生收益。

## 平台与微前端的代价

应用 shell 可统一导航、认证、配置与监控，业务只调用稳定平台接口。插件系统还需定义注册、启动、卸载、权限和协议版本，不能只允许任意代码注入。

| 集成方式                    | 收益                     | 主要成本                     |
| --------------------------- | ------------------------ | ---------------------------- |
| 构建时包集成                | 类型协同与统一优化较直接 | 发布仍可能耦合               |
| Runtime / Module Federation | 可独立交付模块           | 版本、加载和运行时故障       |
| iframe                      | 独立文档与样式环境       | 通信、导航与可访问性整合     |
| Web Components              | 元素与样式封装能力       | 数据、依赖和发布协议仍需治理 |

Iframe 的安全隔离还取决于同源关系、sandbox 和通信协议；不能把独立文档直接理解为完整安全沙箱。Module Federation 共享 singleton 也需要版本兼容和失败策略。

微前端增加重复依赖、网络与调试成本，无法修复混乱的领域边界。单应用模块化能满足团队时，通常更容易维护。平台团队提供稳定通路与支持，不应成为所有业务修改的瓶颈。

## 渐进迁移保留一个真值来源

先建立旧行为基线和关键测试，选取路由或功能切片，让新实现逐步接管。Adapter 转换旧接口，隔离层阻止旧数据模型扩散到新模块；新旧代码不要各保存一份无法协调的共享状态。

机械变化可用 codemod，行为变化通过灰度验证。每步观察错误、性能、业务成功率和接管比例，保留可切回边界。重写只有在旧系统无法安全演进且迁移边界可重建时才值得考虑。

## 一份能讨论的方案

以“订单导出拖慢首屏”为例：先给证据和目标，再比较保持现状、延迟加载、服务端异步导出。说明每种方案对等待、失败恢复、维护和基础设施的影响。

方案还应写清非目标、兼容期和可执行回滚阈值。例如“先迁移只读订单列表，不改变付款协议”，能防止讨论无限扩展；达到哪些错误率或成功率变化就停止灰度，也要在上线前约定。

ADR 记录背景、约束、选择、后果与复审条件。依赖图解释静态关系，时序说明运行过程；未知项用实验验证。上线方案还要写明灰度、监控和回滚，不能只写最终结构。

性能评审同时检查路由、组件和数据加载边界，避免拆包后又形成串行瀑布。可靠性目标可用关键操作成功率等 SLI，SLO 是目标，错误预算表达容许失败额度；如何观测见[告警与恢复](../monitoring/operations.md)。
