# 性能策略与预算：让收益进入日常交付

首屏 HTML 更早到达，却仍要下载大量 JS 才能点击，这说明渲染策略与交互成本需要一起设计。

## 按页面选择渲染方式

| 策略       | HTML 在哪里生成    | 适合考虑的条件                 |
| ---------- | ------------------ | ------------------------------ |
| CSR        | 客户端             | 强交互、内容主要在登录后       |
| SSR        | 请求处理时         | 个性化或及时更新内容           |
| SSG        | 构建时             | 可提前生成的内容               |
| 增量再生成 | 静态结果按策略更新 | 允许受控陈旧、需要降低重建成本 |

这些是工作方式，不是性能排名。SSR 可能受后端与数据等待拖累；SSG 要考虑更新和缓存；CSR 需要控制首屏请求链。

Hydration 将客户端逻辑关联到服务端 HTML，可见不等于已交互。时间、随机数、环境分支或初始数据不一致可能导致 mismatch。流式 HTML 让部分内容先到达，选择性激活或 islands 可减少一次性工作，但具体能力依框架和版本。

路由、组件与数据加载边界应一起设计：提前加载页面代码却仍串行获取必要数据，收益可能有限。大屏可分离数据聚合、计算与绘制，大表单按字段订阅，不能只用 SSR/CSR 名称解释全部性能选择。

## 第三方要算入预算

统计、客服与广告消耗网络、主线程和内存。Async/defer 改变时机，不能消除执行成本。先建立用途、owner 和成本清单，再选择需要时加载、受控超时、故障降级与隔离。

Iframe 隔离文档不等于隔离设备资源；Worker 不能执行依赖 DOM 的 SDK。服务端转发或自托管会转移维护、更新与数据处理责任，并非免费优化。涉及同意要求时，加载时机还应满足实际数据处理约束。

## 用三层预算防止回退

构建检查关键资源体积与新增依赖，实验室检查固定路径的加载与交互趋势，线上 RUM 观察真实分布和长尾。任何一层通过，都不能替代其余证据。

预算应按页面与设备制定，记录基线、目标、owner、例外和到期时间。CI 固定环境，明确冷热缓存，多次运行比较并留噪声容差；失败时展示具体新增资源或调用成本，而非只给一个分数。

例如列表路由新增图表依赖，先判断首屏是否必需，再比较延迟加载前后的关键路径、交互和下一步等待。把首屏工作移到点击后，不代表整个用户流程更快。

架构决策见[演进与评审](../architecture/evolution.md)，预算落地可参考 [Lighthouse CI](https://googlechrome.github.io/lighthouse-ci/docs/)。
